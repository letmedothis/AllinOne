# AllinOne 静态审查接管与修复设计

## 目标

接管 Zcode 尚未完成的静态审查任务，在保留当前 `main` 工作区既有未提交修改的前提下，完成原 93 项问题的剩余修复、复核当前改动引入的回归，并形成可追溯的静态证据清单。

## 强制边界

- 仅执行源码、配置、SQL、文档、Git 差异和代码知识图谱的静态检查。
- 不运行编译、测试、应用、数据库、浏览器、lint、构建或性能测试。
- 不把静态检查通过表述为可编译、可运行、可发布或业务验证通过。
- 不覆盖、清理、回退或混合提交用户已有修改。
- 不引入新依赖，不执行数据库迁移；SQL 修复仅修改仓库脚本和文档。

## 实施策略

采用“原清单收口 + 当前差异回归复核”的混合方案。

### 批次一：鉴权和票据

处理 Jimu ticket 原子消费、目标绑定、敏感日志、长期 JWT 回退、授权版本失效覆盖，以及菜单搜索 XSS。相关前后端文件由同一个实现智能体独占，避免票据契约分叉。

### 批次二：回写与字段映射

统一字段映射保存契约和运行时回写契约：使用原始单元格值、按数据类型转换、拒绝缺失主键或普通字段、拒绝重复目标列，并解决模板归属更新的前后端不一致。

### 批次三：WorkReport 与数据生命周期

修复请求体类型转换回归、负坐标和顺序、授权幂等、逻辑删除谓词、模板状态校验、草稿和单元格孤儿数据问题。

### 批次四：Quartz、Mapper 和系统模块

收口调度器启动清理、暂停任务立即执行、数据库与 Scheduler 状态分叉，以及分类树、逻辑删除、审计字段、公告和字典缓存问题。

### 批次五：前端可靠性

修复编辑器异步加载覆盖、部分保存状态、可见范围计算、列表请求 latest-wins、错误状态误报和前端生命周期泄漏。

## 多智能体协作方式

1. 每个批次由一个实现智能体独占明确文件集合，避免共享文件并行写冲突。
2. 实现后由独立的规格复核智能体检查是否覆盖报告项且无越界修改。
3. 规格通过后由代码质量复核智能体检查正确性、安全性、维护性和前后端契约。
4. 发现问题时退回原实现智能体修改，并再次复核。
5. 主智能体负责检查 Git 差异、协调文件所有权、维护问题状态和最终静态证据。

## 静态验收标准

每个问题必须记录以下状态之一：`已静态确认`、`静态未完成`、`误报`、`需要动态验证`。

判定为“已静态确认”必须同时满足：

- 报告描述的错误路径在当前源码中已消失。
- 调用方、实现、Mapper/SQL、前端 API 或权限配置之间的契约一致。
- 当前差异没有引入新的空指针、失败开放、竞态、越权、静默成功或数据残留路径。
- 独立规格复核和代码质量复核均无未关闭意见。

所有依赖并发时序、真实数据库、Redis、Quartz、浏览器或第三方 Jimu 引擎的结论只能标记为“需要动态验证”，本轮不执行对应验证。
