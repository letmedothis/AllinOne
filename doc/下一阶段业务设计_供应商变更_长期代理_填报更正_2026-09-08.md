# 下一阶段业务设计：供应商变更审批、长期代理、已提交填报更正

日期：2026-09-08。状态：业务设计初稿，尚未实现或完成业务验收。文中的审批配置、期限和限制是本轮建议，不代表用户已经确认。

本阶段沿用首轮边界：单订单开票、先收货后审票，期初应付使用专门入口。三项功能共同遵循：审批前保持原有效数据；明确谁申请、谁负责、谁实际办理；生效后保留旧版本；失败不能留下部分生效的数据。

## 3. 供应商变更审批

### 3.1 变更范围与审批路线

已准入且有效的供应商才可发起变更。默认由具备权限且在数据范围内的供应商负责人申请；负责人离职先交接，创建人保留历史记录，不作为永久唯一维护人。

| 字段类别 | 建议规则 | 审批路线 |
| --- | --- | --- |
| 联系人、联系电话、联系地址 | 填写变更原因，支持证明材料 | 采购主管 |
| 开户行、户名、银行账号 | 必须附账户变更证明，财务记录核验方式与结果 | 采购主管→财务复核 |
| 名称变化但税号相同 | 必须附主体名称变更证明，核对账户是否同步变化 | 采购主管→财务复核 |
| 税号变化 | 本轮按新供应商准入办理，禁止把旧供应商替换成另一主体 | 新准入；旧应付及历史订单仍归旧主体 |
| 多类字段同时变更 | 按最严格路线办理 | 包含财务复核则不能省略 |

申请人不得审批自己的申请。财务复核人与本单采购审批人不同；通过代理办理时对实际人员和被代理人员均检查冲突。找不到合法审批人时进入“待配置”，不能自动通过。

### 3.2 状态与生效

变更单：草稿→审批中→已生效；审批中可退回，退回修改后重新提交；草稿/退回可取消；审批中撤回必须与审批竞争同一版本校验，撤回后取消剩余任务。通过后的资料错误需要再发一张变更单。

一供应商同一时间最多一张未结束变更单（含草稿、退回、审批中）。创建时保存基准有效版本；提交、最终批准均核对基准版本。版本过期时展示差异，要求重新核对后提交，不自动覆盖。

最终批准与资料新版本、有效版本切换、审批日志在同一事务完成。前序节点通过不改变有效资料。列表始终展示有效资料，并标注“有变更审批中”；详情分为有效资料、变更申请、历史版本。

### 3.3 对订单、应付、付款的影响

- 历史订单、发票、期初应付保留当时供应商名称/主体快照及版本引用，不随主档更新改写；应付余额继续按供应商稳定 ID 归集。
- 付款提交时固定收款账户及账户版本，财务复核、执行付款页面都展示该快照，不能执行时静默读取新账户。
- 账户或主体名称变更提交后，该供应商尚未执行的付款进入“资料变更待核对”阻断，仍可查询及审批，不能登记执行；普通联系方式变更不阻断付款。
- 变更退回或撤回后解除这张申请产生的阻断，不移除其他阻断。已生效的账户/名称变更使受影响未付款单的账户确认失效；更新快照后从财务复核重新审批，超过原有金额门槛仍需终审。保留原审批记录，不能沿用旧批准。
- 待复核期间保留付款对发票余额的占用，避免重复申请；主动取消付款则按现有余额释放规则处理。
- 财务登记执行与变更提交/生效对同一供应商采用一致锁顺序：已完成的支付事实不可改写；先进入变更阻断的付款不得继续执行。系统外已经汇出的款项需提交真实支付凭证走异常核实，不能通过修改账户掩盖事实。

例：账号 A 改为 B。审批期间主档仍是 A，但执行受阻；批准后主档是 B，原待付款必须换用 B 并重新复核；历史已付款仍显示 A。

## 4. 长期代理

### 4.1 授权对象与范围

长期代理是持续一段时间的代办授权，责任人不变。单次转交是任务交接；永久离职采用负责人/任务交接，不依靠无限期代理。

授权单必填：委托人、代理人、原因、开始/结束时间、业务类型、节点、部门/公司范围。可选金额上限仅用于已有金额字段且含义明确的单据，以本币金额校验；代理限制不能放宽原审批门槛。

建议默认 30 天，单次最长 180 天，到期可重新申请；服务端以开始时间包含、结束时间不包含判断有效性，统一时区。管理员代建必须记录原因与原责任人，仍走审批。

首版仅代理审批与退回，覆盖旧审批、Flowable 采购订单、付款复核/终审以及本阶段两个新业务。实际付款执行、系统配置、账号管理、批量导出和代填代提交不随授权开放。

代理人须为有效在职账号，本身具备该节点业务资格和办理权限。授权额外赋予指定任务及必要附件的最小读取范围，不扩大其日常列表、供应商全量查询或报表权限。查看与操作接口都校验授权，不只控制按钮。

### 4.2 授权审批与生命周期

建议由委托人所属业务范围的主管批准；财务节点增加财务负责人复核。申请人、委托人、代理人不能批准该授权；主管自己委托时走有管辖权的上级。无人符合资格则待配置。

草稿→待审批→待生效/生效中→已到期；待审批可退回或撤回，待生效/生效中可撤销。已批准授权不能直接修改代理人、范围或期限，变更应重新申请。

委托人可撤销自己的授权，有管辖权的授权管理员可撤销并写明原因。任一账号停用、相关角色失效或组织变动使既定授权范围失配时，实时暂停代理并进入管理异常清单。恢复需重新核验，不能随账号启用自动恢复。

禁止自我代理、代理链、循环代理；同一委托人相同业务/节点/范围的时间段不能重叠。续期不自动延长旧授权。有效期内默认覆盖该责任人的现存及新增未完成任务。

### 4.3 待办与办理规则

- 待办分“本人”“代理”，同一任务只计一次；代理任务显示“代某某办理”和到期时间。原责任人仍可办理，任一人完成即移除双方待办。
- 任务保留责任人；每次操作另存实际操作人、代理授权 ID、授权版本及当时节点，不伪造委托人登录身份。
- 发起人不能借代理审批自己的单据；同一实际人员不能通过代理连续承担必须分离的复核/终审节点。职责分离同时检查实际操作人和责任人历史。
- 打开页面不等于取得办理权。提交决定时重新检查期限、撤销、资格、数据范围和任务版本；委托人与代理人同时操作只能成功一次。
- 到期/撤销与办理通过事务内授权状态校验和锁确定顺序：已提交成功的审批保留；失效后的请求拒绝。待办是否显示不能作为授权依据。
- 已处理任务仍可按审计权限查历史；代理到期即失去依靠代理获得的待办和附件访问能力。

实现上以统一的“办理身份与授权校验”服务接入各审批入口；Flowable 不宜把长期代理直接实现成反复 `setAssignee`。角色候选型付款节点需核对委托人确实可处理当前单据，不能凭代理关系获取全体付款权限。

## 5. 已提交填报更正

### 5.1 申请与审核

入口在已提交填报详情“申请更正”。复制当前有效版本生成独立草稿，原记录继续生效。申请人默认是原填报负责人或经过交接的负责人，且具备该记录的数据权限；必须填写原因，支持补充证明。

同一填报最多一张未结束更正申请。编辑器加载原模板版本与原字段映射版本，工作表及索引完整保留，不自动切到最新模板。修改模板、填报主体、归属部门、期间或回写主键不属于普通内容更正，首版阻止并提示专门迁移/调整流程。

更正单：草稿→审核中→已生效；可退回再提交，未生效前可取消/撤回并检查版本。审核人按模板及原归属部门配置，不能为申请人；被代理身份也须符合分离要求。未配置合法审核人时不能提交。

已封账期间禁止直接更正。尚无统一封账模块时，按模板配置可更正期间；涉及封账控制但未完成配置的模板不开放更正。原模板停用不阻止合法历史更正；模板缺失或回写目标结构不兼容则阻止并交管理员处理。

### 5.2 差异与版本

审核页面按工作表展示单元格位置、字段名称、原值、新值；区分新增、修改、清空与公式变化，不能把清空当作“没有修改”。数值按原始值比较，展示格式单列；公式及其结果都保留。重要公式的结果校验策略由模板定义，不能仅相信浏览器缓存结果。

更正内容版本号与并发修改版本号分开。每个已提交/已生效内容版本保存完整工作簿、完整单元格快照、模板和映射版本、提交人与时间、原因、审批及附件引用。原有效版本不可删除或覆盖。

审批中报表继续用旧有效版本；更正生效后，报表只读取新的有效版本，不能把两版相加。历史导出标明内容版本及“历史版本”，已有导出文件不会自动变化；当前导出记录导出时间和使用版本。

### 5.3 回写与生效一致性

首版只开放无回写，或同一事务数据库内、支持来源追踪和冲突校验的回写模板。外部数据源、缺少来源记录、多个填报共同覆盖同一目标字段等场景先显示具体原因，不冒险执行更正。

每次回写记录来源填报/内容版本、目标表及业务键、受控字段、写前值、写后值与校验摘要。正式生效前锁定原有效版本和目标记录，确认目标仍是上次本来源写出的值；如果被其他业务改动，阻止本次生效，保留旧有效版本并展示冲突。

最终审核通过、完整快照写入、目标字段更新、有效版本切换、审计事件须同事务成功；任一步失败整体回滚，申请仍待审核并显示失败原因。重试使用请求幂等标识，不能重复回写。异步报表缓存刷新通过事务事件重试，页面显示数据更新时间。

清空单元格按字段的可空规则写入 NULL 或经定义的空值，不跳过旧值；禁止由通用更正删除其他来源记录。本阶段不支持改变目标主键，避免出现旧目标残留和新目标重复。更正仍不能直接写入供应链单据、审批及支付事实表。

例：9 月数量 100 更正为 80。审核期间汇总仍为 100；生效事务成功后为 80；历史查询可看到 100，不能汇总为 180。若回写目标已被其他业务改为 90，更正失败并提示冲突，不能直接覆盖成 80。

## 6. 数据与接口落点（建议命名）

| 模块 | 建议持久化对象 | 关键约束 |
| --- | --- | --- |
| 供应商变更 | `supplier_change`、`supplier_profile_version`；付款补账户快照及确认状态 | 基准版本、每供应商唯一未结束申请、不可变版本、付款阻断来源 |
| 长期代理 | `approval_delegation`、授权审批/状态事件；任务决定补办理身份 | 时间范围防重叠、责任人/实际人分列、授权版本、实时失效 |
| 填报更正 | `collect_correction`、`collect_data_version`、版本单元格、映射版本、回写来源记录 | 每记录唯一未结束申请、有效版本指针、不可变历史、回写幂等 |

唯一未结束申请和授权重叠检查必须通过数据库约束或锁保证并发正确，不能仅依赖页面检查。所有列表分页，详情/附件/导出沿用同一权限判定；浏览器 ID 使用字符串。

建议接口分为申请草稿保存、差异预览、提交/撤回、审批决定、历史查询。决定请求必带申请版本和幂等标识；服务端生成审批路线与差异，不接受前端指定任意状态或审核人。供应商和填报新流程复用审批适配层，但业务生效由各自 Service 执行，不能由通用审批直接改业务表。

建议权限按 `supply:supplierChange:*`、`system:delegation:*`、`collect:correction:*` 分组，并单独区分新增、查询、审批、管理；长期代理不会自动授予管理权限。所有异常提示给出可处理原因与入口，如“原资料已更新，请重新核对差异”，不只显示操作失败。

1. 普通资料变更审批中不影响有效资料；退回重提可见逐轮差异和附件。
2. 账户变更与付款执行并发时只出现合法顺序；审批通过后的待付款不能使用旧账户直接执行。
3. 两人同时发起供应商变更仅一张有效；过期基准不能覆盖最新资料。
4. 非管辖主管、无节点资格人员、申请人本人及存在身份冲突的代理均无法批准。
5. 委托人和代理人同时处理只有一次成功；授权到期/撤销后，已打开页面也不能办理。
6. 代理不能访问范围外单据或复用附件链接；角色撤销、账号停用及时生效。
7. 更正提交后报表仍显示旧值；批准后只统计新版本，历史版本完整可查。
8. 跨工作表修改、清空、公式修改和精确小数的差异与回写一致。
9. 回写中途失败全部回滚；目标被他人改动拒绝覆盖；重复请求不产生重复生效。
10. 模板下架、映射后来修改、旧版本缺失、封账期间各有明确处理路径。

迁移原则：先新增结构和权限，再回填可证实的初始版本，核对数量与摘要，再开放入口。供应商当前资料可记为迁移基线，不能声称还原全部历史；历史填报模板/映射无法还原的记录保留只读并列入迁移异常清单，不套用最新版本。上线后产生新版本的数据不应通过简单删表回退；恢复方案需包含版本、任务、回写表和附件的一致备份。

业务评审重点：主管/财务审核人配置、代理 30/180 天期限、账户变更期间付款阻断规则、模板可更正期间。当前均已给出可执行默认设计，后续可据实际组织制度调整。
