## 2. 组织与数据权限设计(按职级)

### 2.1 用户-部门-职级模型

- 部门:采购部 / 财务部 / 信息部 / **仓储部(新增,收货确认)**(挂 RuoYi `sys_dept`;信息部定位系统维护(管理员),不参与业务审批)。
- 职级(建议新增独立维度,而不是塞进角色):`总监`、`部门领导`、`职员`。
  - 采购部:采购总监(看全部)、采购经理(本部门)、采购职员(本人);
  - 财务部:财务总监、财务经理、财务职员;
  - 仓储部:仓储负责人(本部门)、仓管员(职员,收货确认,对"已批准订单"有读取例外);
  - 信息部:系统管理员(IT 维护,数据范围全部但只做运维操作)。
- 建议落地方式(需与实现现状核对后定):
  1. `sys_user` 增加扩展字段 `rank_level`(EXEC / LEADER / STAFF)或复用"岗位"承载职级;
  2. 查询时按 `(部门, 职级)` 计算可见集合:**总监 → 全部门数据;部门领导 → 本部门;职员 → create_by = 本人**;
  3. 现有 `supplyGlobal`(角色级全局)改由职级判定,保留管理员=全部。

### 2.2 已确认 / 待定边界

- ✅ 部门领导"看本部门"= **仅本部门,不含下级**;
- ✅ 收货/入库由**独立仓储部**执行(仓管员收货确认;入库确认的"待收货订单可见性"按角色例外建模,见 §1.2 注);
- ⏳ 仓储部的职级/岗位明细(负责人 = 部门领导?仓管 = 职员?)待组织架构图确认,默认按此假设;
- ✅ 审批任务不受数据范围限制:被指派的审批人必须能看对应单据,列表/详情/统计/导出遵循 §2.1。

## 3. 新增:付款 / 应付核销模块(设计要点)

> V1.0 边界外,需新写详细设计,建议作为 V2.0 设计文档一部分。

- 应付来源:已通过发票登记为应付(按发票、可按供应商汇总);作废发票移出应付。
- 付款单:**采购部经办人申请(核销发票、金额=应付)→ 财务部复核(核票、资金计划)→ 财务总监终审(金额分档,小额止于财务复核)**;一笔付款可核销多张发票;核销金额≤应付余额、禁止超额、允许部分核销;防重复付款(幂等键 + 供应商/发票维度校验)。
- 审批链:采购部经办人申请 → 财务部复核 → 财务总监终审(金额分档,待财务确认分档阈值)。
- 状态机:草稿 → 审批中 → 已付款(标记实际付款动作)→ 已核销;退回/撤回释放已占用应付。
- 台账联动:付款单关联发票,发票关联订单/入库行,保持全链追溯;应付账龄(未核销金额按发票日期/到期日)可在台账中心展示。
- 边界建议:银行对接与流水导入、银行回单 OCR 不进 V1(可留接口);"审批通过 ≠ 已付款"改为"付款单生效 = 实际付款"。

## 4. 发票模块重做:真实数电票

- 解析目标:符合税务机关数电票规范的 **XML**(全电发票开具/交付的 XML),不是演示样例。
- 关键差异:
  - 票号为数电票号码(20 位),去重键仍为"销方税号 + 票号";
  - 票面要素(销方/购方名称税号、开票日期、合计金额、货物或应税劳务清单行、含税/未税与税额)按真实结构映射;
  - PDF / OFD 原样上传存附件(不解析内嵌数据);
  - 解析结果人工确认 + 差异说明的交互保留;解析失败保留原件人工录入。
- 交付方式:用**真实票样**(脱敏)驱动解析器开发与回归测试;当前 `InvoiceXmlParser` 的 Demo 分支保留用于演示,生产解析走新解析器。
- ✅ 边界已确认:V1 只做**蓝字数电票**解析登记,PDF/OFD 附件存档;红字(负数/冲红)与进项勾选/税务验真留后续版本。

## 6. 工作区在途改动(WIP)审计与引擎策略

### 6.1 WIP 现状(未提交)

- **Flowable 7.2 引擎已实质接入采购订单**:`pom.xml`/`allinone-supply/pom.xml` 加依赖;`application.yml` 配置 ACT_* 建表与异步执行器;`FlowableTaskExecutorConfig` 提供线程池;新增 `WorkflowEngine*`(Controller/Service/Mapper/测试)、BPMN 资源、`workflow_designs`/`workflow_action_logs` 表与"流程待办/流程设计/流程详情"菜单及前端页面;`PurchaseOrderServiceImpl.submit` 已改为调用 `workflowEngineService.startPurchaseOrder(...)`,注释明确"历史 workflow_* 实例仍由原审批中心处理"。
- **供应商、发票仍在原内置固定流**(`workflow_configs` + `ApprovalController`)。
- 同批未提交内容还包含:报表模块 JimuReport 定义管理(新 domain + `report/config` 页面)、若干接口/页面小改。

### 6.2 结论与建议

1. **方向认可**:真实企业有多角色、可调整的审批需求,统一到 Flowable 是合理选择,建议按此方向走完,不再回退内置流程。
2. **消除双引擎**:供应商与发票审批需在后续里程碑迁移到同一引擎;迁移期间要守住 V1.0 §10.3 约束——同一单据不得同时被两套流程驱动(现状注释已按此处理:新旧按单据/版本分流)。
3. **生产化注意**:ACT_* 首次启动自动建表,生产初始化后应设 `FLOWABLE_DATABASE_SCHEMA_UPDATE=false`;异步执行器与业务事务的一致性(提交后启动流程失败的回滚路径)需要专项测试。
4. **验收补充**:17 章用例之外,新增引擎类用例(启动失败补偿、任务转交、退回后重新提交从首节点开始、并发生成待办)。
