# AllinOne 生产操作设计复盘：多角色视角

日期：2026-09-07。范围：当前工作区中的 V1/V2 需求、供应链前后端与数据库、填报模块、报表鉴权集成和 Docker 交付文件。

本次采用静态调用链核对，并运行现有前端契约测试；没有连接生产数据库，没有执行部署、迁移或真实付款，没有修改业务代码。因此，“已确认”指源码中可直接确定的实现行为；涉及现场发生频率、真实账号授权及运行环境的问题，另列为试运行验证项。

## 1. 对产品意图的理解

我的理解是：你希望把企业里分散在 Excel、聊天记录、审批记录和票据文件里的业务，整理成一个私有化部署的协作系统。业务人员录入一次，后续人员围绕同一份业务事实完成审批、收货、核票、付款，管理人员能从台账追溯到单据和原始附件。

项目可以分成三个部分：

1. 通用能力：若依的账号与权限、Luckysheet 填报、积木报表与展示。
2. 供应链业务：供应商准入 → 订单 → 分批入库 → 发票双审 → 付款与核销。
3. 可信记录：版本快照、附件、审批意见、业务审计、统计与导出。

前两部分已有不少实现，第三部分在付款、新旧审批衔接、权限一致性和异常更正方面尚未贯通。当前更接近需要开发人员协助的业务试用版本，还不足以让各岗位独立处理日常业务和异常。

这里有一个仍需产品负责人明确的定位选择：供应链是通用平台的一个业务应用，还是当前主要交付产品？本报告按“供应链是当前主要交付业务、通用能力继续复用”评估。单公司、单账套、小规模和蓝字数电票是既定边界，不把多租户、红票、税务验真等排除项直接当成缺陷。

## 3. 上线前必须处理的问题

### P0-01：付款单从保存到提交存在连续阻断

**已确认，实施缺陷。**

- 页面新建付款不会填写 `thresholdExceeded`，服务端创建也未设置；插入语句显式绑定该值，而表字段是 `NOT NULL`。严格模式下这会导致保存失败，数据库默认值不能替代显式传入的 NULL。
- `insertPaymentLine` 使用 `#{createTime}`，但 `PaymentLine` 没有这个属性或 getter。即使先修复主单，也会在明细参数绑定时失败。
- `submit()` 使用 `load()` 读取主单，然后对 `payment.getLines()` 求和。`load()` 只执行 `selectById`，该映射没有加载明细，明细列表默认为空。因此，已存付款草稿也会被判为“付款金额必须大于 0”。

**用户后果：** 采购无法完成有效付款申请。不能把付款页面已经存在视作闭环已经完成。

**建议：** 一次性贯通“创建并返回主单 → 重开核销明细 → 提交 → 审批”，统一服务端补齐字段；使用真实 MySQL 执行完整场景。

证据：[付款创建与提交](D:/Develop/Project/AllinOne/allinone-supply/src/main/java/com/allinone/supply/service/impl/PaymentServiceImpl.java)、[付款映射](D:/Develop/Project/AllinOne/allinone-supply/src/main/resources/mapper/supply/PaymentMapper.xml)、[明细对象](D:/Develop/Project/AllinOne/allinone-supply/src/main/java/com/allinone/supply/domain/PaymentLine.java)、[建表](D:/Develop/Project/AllinOne/sql/allinone_biz.sql)。

### P0-02：10 万元分档未成为服务端可靠约束

**已确认，潜在缺陷；正常提交流程当前先被 P0-01 阻断。** `submit()` 算出局部变量 `exceeded`，却没有持久化；复核时仍读取数据库里的 `thresholdExceeded` 决定是否进入总监终审。创建时该字段又来自请求对象。

**用户后果：** 单独修通提交后，大额付款可能仍按错误的分档执行，无法保证“超过 10 万必须终审”。

**建议：** 按保存后的明细总额在服务端判定并落库，拒绝由客户端决定审批级别；分别验收 99,999.99 元、100,000 元和 100,000.01 元，以及退回后改金额的情况。

证据：[分档计算及复核](D:/Develop/Project/AllinOne/allinone-supply/src/main/java/com/allinone/supply/service/impl/PaymentServiceImpl.java)。

### P0-03：发票作废没有检查关联付款

**已确认，跨模块缺口。** 发票作废只释放 `invoice_allocations` 的数量分配，没有查询 `payment_lines/payments`，没有阻止作废已被在途或已生效付款引用的发票。

**用户后果：** 发票从应付查询中消失，但付款记录仍在；若款项已执行，账目无法沿一致的事实链解释。

**建议：** 已有在途占用的发票先处理付款申请；已有实际核销的发票必须进入受控更正流程。即使冲正暂不纳入本版，也应先阻断不一致的作废操作。

证据：[发票作废服务](D:/Develop/Project/AllinOne/allinone-supply/src/main/java/com/allinone/supply/service/impl/DocumentLifecycleServiceImpl.java)、[生命周期映射](D:/Develop/Project/AllinOne/allinone-supply/src/main/resources/mapper/supply/DocumentLifecycleMapper.xml)、[应付查询](D:/Develop/Project/AllinOne/allinone-supply/src/main/resources/mapper/supply/PaymentMapper.xml)。

### P0-04：部署文档把清空持久化数据作为更换密码的步骤

**已确认，生产操作风险。** `docker/README.md` 的注意事项要求数据库密码更换后用 `docker compose down -v` 重置数据卷。项目的数据库、Redis 和附件都使用命名卷，这一步会清除该部署管理的这些数据卷。

**用户后果：** 运维按文档轮换密码，可能丢失业务数据库和附件。

**建议：** 将生产密码轮换改为现有数据库内变更账号密码、同步应用配置、验证连接；清卷仅列入明确的空库演示重置流程。备份必须包含附件及恢复演练，不能只有数据库导出。

证据：[部署文档](D:/Develop/Project/AllinOne/docker/README.md)、[持久化卷配置](D:/Develop/Project/AllinOne/docker-compose.yml)。本次没有执行任何清卷操作。

## 4. 业务设计与用户操作问题

### P1-01：审批通过与实际付款没有可核验的边界

**已确认实现，设计本身需要重审。** 当前复核或终审通过就写 `APPROVED`，页面显示“已付款”。付款模型没有实际支付日期、支付账户、执行人和回单关联等事实字段。即使在银行系统手工付款，应用也需要记录执行结果。

建议明确“审批通过 → 待执行 → 已支付 → 核销”的关系；小团队可以在一次确认操作中同时记录支付与核销，但该操作必须包含实际支付信息。支付失败、重复点击和银行退回要有明确处理规则。

证据：[付款状态更新](D:/Develop/Project/AllinOne/allinone-supply/src/main/java/com/allinone/supply/service/impl/PaymentServiceImpl.java)、[付款页面](D:/Develop/Project/AllinOne/allinone-typescript/src/views/supply/payment/index.vue)、[付款模型](D:/Develop/Project/AllinOne/allinone-supply/src/main/java/com/allinone/supply/domain/Payment.java)。

### P1-02：应付余额混入了审批占用

**已确认，指标语义问题。** 应付查询把 `IN_REVIEW` 和 `APPROVED` 一起扣减，页面同时称为“已核销/占用”和“应付余额”。例如票面 10 万、正在审批 6 万、尚未实际支付，系统会展示余额 4 万。

应分别展示：票面应付、已支付核销、在途申请占用、实际未付、可继续申请金额。按开票日期排序也不足以表达逾期；需要账期/到期日后才能区分“票开得早”和“已经到期”。这是系统金额定义的复盘，不涉及外部会计或税务合规结论。

证据：[应付汇总 SQL](D:/Develop/Project/AllinOne/allinone-supply/src/main/resources/mapper/supply/PaymentMapper.xml)、[应付弹窗](D:/Develop/Project/AllinOne/allinone-typescript/src/views/supply/payment/index.vue)。

### P1-03：付款审批人无法在当前页面充分核对业务

**已确认。** 付款列表没有通用详情动作，只有草稿/退回状态能编辑；审批弹窗只有意见和通过/退回按钮，没有展示核销发票、申请说明、附件及关联业务。后端虽有详情接口，前端审批未使用。

付款仅保存复核/终审意见，没有独立的复核人、终审人、各阶段时间与版本记录；退回后再审会覆盖意见。Controller 有通用操作日志，因此不是“完全没有日志”，但它不能替代业务单据上可追溯的审批历史。作废原因校验后未落入付款业务记录，也存在同类问题。

建议提供付款只读详情及每轮审批记录，再开放审批操作。分档大额若要求两人复核/终审，还需明确定义两岗位能否由同一人承担；当前只排除了申请人自审。

### P1-04：发票草稿和退回流程在页面上断开

**已确认。** 发票列表只有展示列，没有详情、重开编辑或退回处理动作。页面保存后依赖内存中的 `documentId` 继续办理；刷新或下次登录后，没有页面动作把已有发票加载回来。提交后也没有清空表单并明确开始下一张发票。

上传 XML 只加入附件队列，解析需要另行粘贴 XML 文本。人工还要填写订单及订单行 ID。

建议优先做“上传并解析 → 选择可开票订单及明细 → 保存/重开 → 核对差异 → 确认提交”，补明细删除、金额预览、退回意见和提交后去向。另一个细节：确认接口确认的是数据库里的已保存内容，页面应避免让用户以为未保存的改动已经被确认。

证据：[发票页面](D:/Develop/Project/AllinOne/allinone-typescript/src/views/supply/invoice/index.vue)、[发票确认与提交](D:/Develop/Project/AllinOne/allinone-supply/src/main/java/com/allinone/supply/service/impl/InvoiceServiceImpl.java)。

### P1-05：仓储作业缺少可发现入口及误录更正

**已确认。** 收货页面要求输入“已通过订单 ID”和“仓库 ID”；没有待收货选择器，也没有已确认收货列表。后端提供余额校验和入库快照，但生命周期明确拒绝作废入库，提示使用尚未提供的后续更正流程。

建议补待收货清单、仓库下拉、历史批次和结果详情；明确误录数量、选错仓库、短收结案和退货的处理方式。若首版只支持普通货物采购，要把服务采购/无入库业务排除在试点范围外。

证据：[收货页面](D:/Develop/Project/AllinOne/allinone-typescript/src/views/supply/receipt/index.vue)、[收货服务](D:/Develop/Project/AllinOne/allinone-supply/src/main/java/com/allinone/supply/service/impl/ReceiptServiceImpl.java)、[生命周期服务](D:/Develop/Project/AllinOne/allinone-supply/src/main/java/com/allinone/supply/service/impl/DocumentLifecycleServiceImpl.java)。

### P1-06：审批入口分裂，工作台会漏计任务

**已确认。** 供应商/发票使用旧审批中心，采购订单用 Flowable 待办，付款在付款列表内审批。工作台只统计 `workflow_tasks` 中的待办，没有合并 Flowable 和付款。

旧审批中心缺业务详情，且类型展示把所有非供应商任务显示为“采购订单”，发票会被误标；“通过”按钮直接发起审批。Flowable 的“详情”主要显示轨迹，没有订单明细与附件。

建议统一工作入口和待办数量，后端可以继续保留不同执行机制。审批页应呈现本轮提交版本、与上次差异、金额与附件。不能要求领导记住哪个业务用了哪个审批引擎。

证据：[旧审批中心](D:/Develop/Project/AllinOne/allinone-typescript/src/views/supply/approval/index.vue)、[流程详情](D:/Develop/Project/AllinOne/allinone-typescript/src/views/supply/workflow/detail.vue)、[工作台查询](D:/Develop/Project/AllinOne/allinone-supply/src/main/resources/mapper/supply/SupplyDashboardMapper.xml)。

### P1-07：权限规则无法从管理员配置完整落到用户体验

**已确认。**

- `rank_level` 已有数据库列和供应链解析器，但检查的 `SysUser`、用户 Mapper 和用户管理页面没有职级字段，管理员无法通过常规用户管理维护。
- 未配职级时回退旧全局角色逻辑，存在“漏配置反而看得更多”的可能。
- 付款列表允许部门领导看到同部门创建的付款，但详情权限没有部门分支，可能出现“列表看得到、点开无权”。
- 应付查询只有功能权限，没有套用供应链行级范围；采购职员与财务职员的应付可见范围需要重新明确。
- 财务角色在付款中可见全部是文档记录过的有意例外，不能当成未经授权的已证实漏洞；但其他模块又按职级限制，必须在产品与配置中解释清楚。
- 通用填报列表按角色数据范围返回记录，详情却只允许本人/管理员。部门领导可以看到成员记录列表，但打不开详情。

建议把“能做什么”“能读哪些单据”“哪些字段能看”“是否承担审批任务”分开建模，统一列表、详情、附件、导出与选择器策略。总监全局可见是现有决定，不应擅自推翻；如再细分业务域，应由业务方评审。

证据：[供应链范围解析](D:/Develop/Project/AllinOne/allinone-supply/src/main/java/com/allinone/supply/support/SupplyDataScopeResolver.java)、[付款范围](D:/Develop/Project/AllinOne/allinone-supply/src/main/java/com/allinone/supply/service/impl/PaymentServiceImpl.java)、[填报列表与详情](D:/Develop/Project/AllinOne/allinone-collect/src/main/java/com/allinone/collect/service/impl/CollectDataServiceImpl.java)。

### P1-08：调岗、离职和审批人缺席缺少业务交接

**已确认部分查询行为，其余为所检查应用入口的缺失。** 供应链多处使用当前 `sys_user.dept_id` 判断历史单据归属，并排除已删除的创建人。调岗或删除用户可能改变部门领导对历史记录的可见性。

检查的供应链控制器、服务和页面没有任务转交/代理办理入口；引擎自身具备相关能力，不代表本项目已经提供给管理员使用。固定流程的候选人配置也不能替代在途任务的交接。

建议保存业务发生时的所属部门，并独立维护当前责任人；停用用户前展示其草稿、在途任务和待收货/待付款业务，要求指定接替人。普通请假应有带期限的代理，不能靠共用账号。

证据：[付款部门查询](D:/Develop/Project/AllinOne/allinone-supply/src/main/resources/mapper/supply/PaymentMapper.xml)、[台账部门查询](D:/Develop/Project/AllinOne/allinone-supply/src/main/resources/mapper/supply/LedgerMapper.xml)、[审批办理](D:/Develop/Project/AllinOne/allinone-supply/src/main/java/com/allinone/supply/service/impl/WorkflowEngineServiceImpl.java)。

### P1-09：主数据通过审批后，正常变更无路可走

**已确认供应商行为。** 已通过供应商不能编辑，而有有效订单的供应商又不能作废。联系人、地址、开户信息发生变化时，没有变更申请流程。将所有字段都锁死会推动用户找管理员直接改库。

建议增加供应商变更单：联系人等普通资料与银行账户等敏感资料使用不同审核要求；历史订单和实际付款保留当时资料快照。公司与仓库初始化也需要管理员可操作的维护入口，不能长期依赖 SQL 演示脚本。

证据：[供应商修改限制](D:/Develop/Project/AllinOne/allinone-supply/src/main/java/com/allinone/supply/service/impl/SupplierServiceImpl.java)、[作废限制](D:/Develop/Project/AllinOne/allinone-supply/src/main/java/com/allinone/supply/service/impl/DocumentLifecycleServiceImpl.java)。

### P1-10：现有模型与部分真实业务情形不相容

**设计限制，需确认试点范围，不能直接视为所有客户都会发生的缺陷。**

- 一张发票主单只关联一个订单。供应商把多个订单合开一张票时，现有票号唯一约束也不允许简单拆成多张相同发票。
- 发票提交依赖已审批订单及可分配入库数量，先票后货不能走正常提交；服务采购也可能没有可供分配的实体入库。
- V2 提出期初应付少量发票人工补录，但正常发票流程要求订单和入库，这与直接录入历史应付有冲突。
- 提交发票的人不能是订单采购审核人或财务审核人。小团队需要明确谁负责登记，否则经办自己建单后会在提交时被拒绝。

建议先确定受支持的采购情形与人员配置。期初余额使用专门的、可审计的初始化入口；不要为了满足现有流程伪造采购订单和收货。

证据：[发票单订单及审核人校验](D:/Develop/Project/AllinOne/allinone-supply/src/main/java/com/allinone/supply/service/impl/InvoiceServiceImpl.java)、[V2 期初口径](D:/Develop/Project/AllinOne/供应链采购审批与票据台账系统_详细设计_V2.0.md)。

## 5. 通用平台与交付问题

### P1-11：填报模板改版可能改变在途草稿的含义

**已确认。** 草稿创建时记录模板版本，但提交时读取当前模板做必填/字典校验，并把记录的模板版本改成当前版本；回写映射也按模板 ID 读取当前配置。模板编辑直接更新同一份定义。

如果管理员在填报期间改了字段位置、校验或映射，旧草稿会按新规则处理；“有版本号”不足以保证内容可还原和解释。

建议绑定不可变的模板发布版本及映射版本。在途草稿继续旧版，或通过明确的迁移提示转换。已提交数据的更正也需有正规入口；页面只提示“联系管理员”，服务端仍禁止修改，不能把直接改库作为长期处理方式。

证据：[填报提交](D:/Develop/Project/AllinOne/allinone-collect/src/main/java/com/allinone/collect/service/impl/CollectDataServiceImpl.java)、[模板更新](D:/Develop/Project/AllinOne/allinone-collect/src/main/java/com/allinone/collect/service/impl/CollectTemplateServiceImpl.java)、[回写映射](D:/Develop/Project/AllinOne/allinone-collect/src/main/java/com/allinone/collect/service/impl/DataWriteBackServiceImpl.java)。

### P1-12：通用表格、供应链和报表需要统一数据治理

**已确认机制不同，尚未验证真实报表的越权行为。** 通用填报按角色数据范围，供应链按职级与任务例外，积木集成提供用户/部门/角色参数；没有证据表明任意报表 SQL 都会自动继承供应链范围。

通用表格的业务回写有白名单，这是已有保护；但如果未来把供应链事实表列入白名单，直接回写将缺少供应链服务层的审批、数量占用和审计约束。当前没有据此确认存在已发生的绕过。

建议让业务模块拥有单据状态和余额，表格作为录入方式调用业务服务；报表通过受控查询接口或视图读取。对每张正式报表登记负责人、数据口径、数据范围和更新时间，使用真实配置逐张验证。

证据：[回写实现](D:/Develop/Project/AllinOne/allinone-collect/src/main/java/com/allinone/collect/service/impl/DataWriteBackServiceImpl.java)、[积木用户上下文](D:/Develop/Project/AllinOne/allinone-framework/src/main/java/com/allinone/framework/jimureport/JimuReportTokenService.java)。

### P1-13：部署成功提示不能证明业务可用

**已确认。** Compose 后端健康检查使用 `curl -s`，未使用 HTTP 错误失败选项，也不检查响应业务码；返回 HTTP 错误仍可能被判健康。文档要求在 `.env` 设置 `FLOWABLE_DATABASE_SCHEMA_UPDATE=false`，但 Compose 的后端没有透传该变量，也没有 `env_file`。

当前应用使用数据库 root 账号；初始化脚本只在空卷执行，不能承担日后每次发布的升级管理。生产运行应分离初始化与应用账号，明确每版迁移、版本记录和恢复步骤。

建议分开提供存活、依赖就绪和关键业务检查；数据库、附件、必要配置成套备份，并在独立环境验证恢复后能打开历史附件和继续在途任务。

## 6. 建议落地顺序

1. **先恢复事实一致性与基本可用性。** 修付款保存/明细/提交/分档，阻断发票与付款不一致的作废，纠正清卷换密码文档。完成真实数据库验证。
2. **再让各岗位能独立工作。** 补发票重开及退回处理、仓储选择与查询、单据详情和审批证据、统一待办。
3. **补齐组织与异常管理。** 职级维护、读写权限一致性、离职交接、供应商变更、收货更正、付款执行与业务审计。
4. **最后形成可交付的运维与配置流程。** 模板发布版本、期初初始化、迁移及备份恢复、岗位手册和业务健康检查。

不建议此时为统一外观而整体替换审批引擎。用户入口和业务规则可以先统一，避免扩大已经存在的验证范围。

## 7. 进入试运行前的角色验收场景

| 场景 | 应通过的判断 |
| --- | --- |
| 采购创建付款并刷新重开 | 主单、明细、金额完整；能够继续提交 |
| 分别申请 99,999.99 / 100,000 / 100,000.01 元 | 小额与大额进入预期节点；客户端字段不能控制分档 |
| 退回付款后改成大额再提交 | 新一轮审批按新金额判定，并保留旧轮次记录 |
| 同一发票有两笔并发付款申请 | 在途合计不超额，失败方收到可理解提示，可安全重试 |
| 发票已有在途或已付款关联后尝试作废 | 被阻止或进入明确的受控更正，不产生孤立付款 |
| 发票保存、退出、重登、退回后重开 | 均可从列表进入正确记录与版本 |
| 仓管仅凭送货单寻找订单并收货 | 不需要数据库 ID，也不暴露非必要财务信息 |
| 收货填错数量或仓库 | 有受控更正路径，保留原始记录，不直接改库 |
| 审批人进入工作台 | 看到旧流程、Flowable 和付款的完整待办；能查看业务证据 |
| 部门领导读取成员记录 | 列表、详情、附件与导出遵循同一可解释范围 |
| 员工调岗、停用或请假 | 历史业务归属稳定，在途任务与责任可交接 |
| 模板在他人填报期间升级 | 旧草稿按绑定版本提交，或明确迁移，不静默改变含义 |
| 人工录入期初应付 | 不需要伪造订单和入库，记录来源及审批责任 |
| 轮换密码并恢复备份 | 业务库与附件完整，在途审批继续可用 |
